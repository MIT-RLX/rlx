# rlx-js

Run JavaScript that drives RLX — build graphs, compile for any backend,
differentiate, **train**, load and convert checkpoints, tokenize, sample —
with no Node, no npm and no C toolchain.

The engine is [`quickrs`](https://github.com/eugenehp/quickjs-rs), a pure-Rust
QuickJS-ng. It links as a normal crate, so `cargo build` yields one static
binary that speaks JavaScript and reaches every backend it was compiled with.

```bash
just js crates/bindings/rlx-js/examples/train_classifier.js
FEATURES=metal,gpu just js crates/bindings/rlx-js/examples/transformer_block.js
cargo run -p rlx-js --bin rlx-js -- -e 'rlx.devices()'
```

## Two spellings, one graph

Threading node ids reads inside-out — the first operation applied is the
innermost token, so you unwrap the expression backwards:

```js
const g = new rlx.Graph("block");
g.setOutputs([g.add(x, g.matmul(g.silu(g.matmul(g.rmsNorm(x, w, b, 1e-6), wg)), wd))]);
```

`rlx.dsl` returns the same `Graph` — `Session.compile` takes it unchanged — but
its sources hand back a chainable `Tensor`, so it reads in the order the data
flows:

```js
const m = rlx.dsl("block");
const x = m.input("x", [1, 8, 256]);              // dtype defaults to "f32"
const h = x.rmsNorm(m.param("nw", [256]), m.param("nb", [256]), 1e-6);
m.output(x.add(h.matmul(m.param("wg", [256, 512])).silu()
                .matmul(m.param("wd", [512, 256]))));
```

`Tensor` carries `.dims`, `.dtype`, `.id` read straight off the graph, so shapes
come from the inference that actually happened rather than from what you
assumed. `m.lift(id)` brings an imperative node back into a chain, and
`m.output` takes Tensors, ids or an array.

In an operand slot a bare number becomes a constant of the receiver's dtype, so
`x.mul(2)`, `x.div(255)` and `x.binary("pow", 2)` read the way they should.
Only the ops whose every operand is a tensor lift — `narrow(1, 2, 3)` is an axis
and two offsets, and lifting those would build garbage. `a.concat([b, c], axis)`
chains too, despite `Graph.concat` taking its list first.

**`Tensor`'s 89 methods are generated by enumerating `Graph.prototype` at
install time**, not from a list kept alongside it. Every op the graph gains is
chainable the moment it is registered, and there is no second table to drift.
[`examples/transformer_block_dsl.js`](examples/transformer_block_dsl.js) builds
the same block both ways and asserts the graphs are **bit-identical** — same
node count, same op kinds, zero delta. The DSL is a spelling, not a second
builder.

## MNIST

```bash
rlx-js examples/mnist.js                    # 784-128-10 MLP
rlx-js examples/mnist.js --cnn              # 1→8→16 conv net
rlx-js examples/mnist.js --steps 5000 --device cpu
```

Real idx-ubyte data, parsed in JavaScript with a `DataView`. Measured on an M4
Pro, Metal, full 10 000-image test split:

| | steps | time | test accuracy |
|---|---|---|---|
| MLP `784→128→10` | 3000 | 4.0 s | **98.00%** |
| CNN `1→8→16→10` | 1500 | 5.2 s | **97.05%** |

```bash
rlx-js examples/mnist.js --save ckpt.gguf        # checkpoint at the end
rlx-js examples/mnist.js --resume ckpt.gguf      # pick up mid-run
rlx-js examples/mnist.js --patience 3            # early stop on validation
```

`--patience` carves a validation split off the *training* data — the test split
stays untouched by any decision the run makes — keeps the best checkpoint rather
than the last, and reloads it before the test sweep.

The script searches the cache directories `rlx-vision-bench` uses, so a prior
download is found; otherwise it prints the `curl` command and exits.

Data preparation is the one place a script does per-element work over tens of
millions of values, so three helpers do it natively:

| | JS | `rlx.*` | |
|---|---|---|---|
| widen + normalize 47 M pixels | 930 ms (`Float32Array.set`, widen only) | **21 ms** (`toFloat32`, widen *and* affine) | 44× |
| assemble 200 batches of 64×784 | 209 ms (`subarray` + `set` per row) | **4 ms** (`gatherRows`) | 52× |
| an interpreted `for` loop | ~8.7 s | — | — |

That took MNIST loading from 1762 ms to **34 ms** and training from 360 to
**756 steps/s**. `gatherRows` got there by *borrowing* the dataset rather than
copying it — the first version read its source with a copying helper and was 4×
slower than the JS it replaced.

## Training

`rlx.Trainer` differentiates the loss graph once, compiles it once, holds the
weights, and returns a scalar loss per step. The optimizer is `rlx-optim`:
Adam, AdamW, Lion, Muon, SOAP, Sophia, LAMB, MARS, RAdam, NAdamW, QHAdamW,
Adafactor, SGD.

```js
const t = new rlx.Trainer(buildLoss(), {
  wrt: ["w1", "b1", "w2", "b2"],
  init: initialWeights,
  device: "metal",
  optimizer: { kind: "adamw", lr: 3e-4, weightDecay: 0.01 },
  clipNorm: 5.0,                           // global gradient-norm clip
});

const result = t.run({
  steps: 3000,
  batch: (step) => nextBatch(),            // null ends the run (data exhausted)
  lr: (step) => cosine(step),              // schedules live in JS
  every: 100,
  onStep: (step, loss) => !stopRequested,  // `false` stops; anything else continues
});
// { steps, stopped, firstLoss, lastLoss, meanLoss, stepsPerSecond, gradNorm }
```

### Start, pause, resume, stop

There is no `pause()` because there is nothing to pause: the loop is synchronous
and every piece of state lives in the handle. Call `run` for a stretch, return
`false` from `onStep` to break out, call it again to carry on from exactly where
it stopped. Across processes, that is `save` / `load`.

```js
t.run({ steps: 500, batch });
t.save("ckpt.gguf");                       // weights + optimizer state + step
// … new process …
const report = t.load("ckpt.gguf");        // {step, restored, optimizerRestored, …}
t.run({ steps: 500, batch });              // bit-identical to never stopping
```

Checkpoints are **GGUF**, so `rlx.openGguf` reads them and so does every other
rlx tool. They carry the optimizer's accumulators, not just the weights:
resuming Adam with its moments reset is a different run, not the same one
continued. `OptimizerState` was added to `rlx-optim` for this, with a test
asserting a checkpointed run matches an uninterrupted one **bit-exactly** for
Adam, AdamW, SGD-with-momentum and Lion. An algorithm that has not opted in
reports `None`, and `load` says `optimizerRestored: false` rather than silently
starting from zero.

### Freezing

Two kinds, and the difference matters:

| | gradient | cost | reversible |
|---|---|---|---|
| left out of `wrt` | not computed | cheaper | no — baked into the compiled graph |
| `t.freeze(["w1"])` | computed, update skipped | same | yes, `t.unfreeze()` |

`t.trainable()` lists what receives a gradient, `t.frozen()` what is held. The
frozen set is saved and restored with the checkpoint, so a resumed run continues
the same recipe.

### LoRA

`loraMatmul` is one fused op — `x·W + scale·(x·A)·B` — so LoRA needs no new
machinery: put the base weight in `init` but not in `wrt`, and only the rank-`r`
factors get gradients. [`examples/mnist_lora.js`](examples/mnist_lora.js) does
the whole story on real data:

```
base    98.00% on normal MNIST · 5.70% on inverted MNIST   <- the shift
adapter rank 8, alpha 16 -> 8 400 trainable (8.3% of the base)
adapt   5.70% -> 93.10% in 488ms (1345 steps/s)
        base weights untouched: true
merged  dense model, no adapter op: 93.10% (agrees)
```

`B` starts at zero so the adapter is an exact no-op at step 0 — the adapted
model begins identical to the base. The merge step folds `W + scale·A·B` back
into a plain weight and checks it scores the same, which is what makes the
adapter free at inference.

[`examples/train_classifier.js`](examples/train_classifier.js) is the small
end: a 2→32→32→3 MLP on a three-arm spiral, **99.7%**. `rlx.Optimizer` is
usable on its own when the script wants to own the loop.

### Optimizer loop cost

`f32Math: true` on `adam` / `adamw` keeps the moment arithmetic in f32 — what
PyTorch does. `rlx-optim` defaults to f64 intermediates, which are slightly more
accurate and measurably slower. Per element, on an M4 Pro:

| | before | after |
|---|---|---|
| `sgd` + momentum | 1.06 ns | **0.15 ns** (7.1×) |
| `adam`, `f32Math: true` | 0.77 ns | **0.37 ns** (2.1×) |
| `adamw`, `f32Math: true` | 0.84 ns | **0.39 ns** (2.2×) |

SGD was the surprise: it did strictly less arithmetic than Lion and took 3.8×
longer, because its hot loop tested `momentum == 0.0` *and* read `self.nesterov`
per element — the latter through a live `&mut self` borrow, which stopped the
loop vectorizing. One specialized loop per configuration fixed it, with the
arithmetic untouched and bit-exactness asserted against the original formulas for
all six configurations.

End to end on a training step (Metal, batch 64): `adamw f32Math` is 1.05× at
101 k parameters and 1.19× at 1.6 M; the SGD fix is worth ~1.2× on its own step.

### Where the optimizer runs

By default it runs on the host: the gradients come back, the update happens on
the CPU, the weights go up again. Measured on an MNIST MLP (102 k parameters,
batch 64) that half is **40–55% of a step and does not vary with the device**:

| device | forward+backward+upload | host optimizer |
|---|---|---|
| cpu | 207 µs | 255 µs |
| metal | 402 µs | 275 µs |
| wgpu | 4825 µs | 302 µs |

`resident: true` fuses the update into the graph instead (`rlx_runtime::train`),
keeping parameters and moments in device buffers so only the scalar loss is read
back. It pays above roughly 200 k parameters — below that the extra dispatches
cost more than the host round trip saves:

| parameters | host | resident | |
|---|---|---|---|
| 101 k | 1920 µs | 2060 µs | 0.93× |
| 407 k | 3673 µs | 2693 µs | **1.36×** |
| 2.1 M | 10747 µs | 6407 µs | **1.68×** |
| 8.4 M | 34067 µs | 16533 µs | **2.06×** |

It is offered only where it is both correct and faster, and says why when it is
not:

| backend | |
|---|---|
| `metal` | verified — matches the host path to 1e-8 over 8 steps |
| `cpu` | refused — no device buffers, so it feeds three extra tensors per parameter and reads three back. Measured **3.3× slower** |
| `wgpu` | refused — the write-back is correct (parameters match to 3e-8 after one step) but the *next* step reads stale values and the trajectory diverges from step 2 |
| others | `resident: "unverified"` to try it; no hardware here to check on |

`isResident()` reports what actually happened, `gradNorm()` returns `null` on the
fused path (the gradients never come back, so there is no honest number to
give), `clipNorm` is refused with it for the same reason, and checkpoints use one
on-disk layout for both paths — a resident run can be resumed on the host path
and back.

## Weights

```js
const f = rlx.openGguf("model.gguf");                  // mmap'd, lazy dequant
for (const name of f.tensorNames()) compiled.setParam(name, f.tensor(name));

const w = rlx.loadPt("pytorch_model.bin");             // also loadMlx/Dduf/Nemo
rlx.toRlxp("model.gguf", "model.rlxp", { from: "gguf" });
rlx.convertToGguf("model.safetensors", "out.gguf", "Q4_K");
rlx.writeGguf("out.gguf", { "blk.0.w": { data: weights, shape: [4096, 4096], dtype: "Q6_K" } });
```

GGUF shapes are GGML order (innermost first), the reverse of safetensors.

`run` is the f32 fast path and **refuses** a graph whose outputs are not all
f32, because the bytes come back reinterpreted rather than converted — a `Bool`
output read that way is `2.37e-38`, not `1`. Use `runTyped({x: {data, dtype}})`,
or `cast(x, "f32")` in the graph. Plausible-looking garbage with no error is the
worst failure mode available, so it is one.

## Precision policy

`policy` selects per-op-kind precision, on the session or per compile:

```js
new rlx.Session({ device: "metal", policy: "mixed" })
session.compileWith(g, { policy: { reduction: "f16", elementwise: "f16" } })
new rlx.Trainer(g, { …, policy: "mixed-conservative" })
```

Measured on a pre-norm transformer block (`[1, 128, 512]`, 8 heads, Metal),
against the f32 run:

| policy | | relative error |
|---|---|---|
| `f32` *(default)* | 715 µs | — |
| `mixed` | 690 µs | 6.3e-4 |
| `mixed-conservative` | 675 µs | 6.0e-4 |
| `f16` | **refused** | returns **all zeros** |
| `mixed-bf16` | **refused** | returns 3.3e38, non-finite |

The last two are refused because they are wrong, not slow. On Metal a *single*
attention op under an f16 policy returns all zeros: the f16 K input routes into
the W8A8 quantized-KV path meant for cache decode, and the arena still holds f32
bytes, so the quantizer reads mantissa bits and rounds them away. Under bf16 the
same read gives `3.3e38` — `HalfFlag` maps BF16 to F32, so bf16 pairs are read as
one f32. A full block under `f16` also produces NaN in `silu` after a matmul.

`mixed` and `mixed-conservative` keep Compute and DataMovement at f32, so they
never reach that path — which is also why the win is 4–6% rather than the 1.5–2×
that downcasting the matmuls would give. An explicit policy touching only
`reduction` / `elementwise` is allowed for the same reason. wgpu ignores the
policy entirely (identical timings and identical output across all five).

## Data path

Tensors cross the boundary as one `memcpy` in each direction, into buffers that
persist across calls — a step loop allocates nothing after the first iteration.
The element-at-a-time `from_ne_bytes` version this replaced did not vectorize
(one bounds check per 4 bytes):

| | before | after |
|---|---|---|
| `setParam`, 1 MiB | 0.127 ms | **0.037 ms** |
| `run`, 1 MiB in + 1 MiB out | 0.220 ms | **0.123 ms** |
| fixed per-call overhead | 1.45 µs | 1.40 µs |

A 256-wide 2-layer MLP trains at ~2500 steps/s on Metal (`[128, 256]` batches,
AdamW). The remaining gap to memory bandwidth is on the output side, where the
runtime returns owned `Vec`s and the engine zeroes an `ArrayBuffer` before it is
filled — both structural, not fixable from here.

## How the surface is generated

Every graph method is the same five steps: read the arguments, borrow the
graph, call one IR builder, wrap the result, register the name. Two macros do
that so a human cannot get it wrong:

```rust
graph_ops! {
    ctx, proto;
    "matmul"(a: node, b: node)                  => |g| g.mm(a, b);
    "softmax"(x: node, axis: i32 = -1)          => |g| g.sm(x, axis);
    "eigh"(a: node) -> pair                     => |g| g.eigh(a);
}
```

`graph_ops!` always reads arguments **before** borrowing the graph handle
(argument conversion can run a getter, and a getter can re-enter the same
graph), and derives `Function.length` from the signature, so a declared arity
cannot drift from the parameter list. `js_class!` does the same for prototypes,
pinning each one non-writable — a swappable prototype would make the class tag
unverifiable, and the class tag is what stands between a bad cast and a wild
pointer. Both invariants have tests.

## Async

QuickJS-ng resolves promises through a microtask queue, but nothing *drives* it
and there are no timers, so `await` only worked on already-settled promises and
`(async () => 1)()` came back as `"[object Promise]"`. There is now a real, if
small, event loop: one timer queue drained in due order, microtasks run to
exhaustion between each, and `eval` **awaits** a returned promise instead of
stringifying it. A promise that can never settle is reported as such rather than
hanging or looking like success.

Single-threaded, so this buys cooperative scheduling, not parallelism — and
nothing here pretends otherwise. Training stays synchronous; yielding is the
script's call:

```js
for (let done = 0; done < total; done += 500) {
  t.run({ steps: 500, batch });
  await rlx.sleep(0);          // let a progress reporter or timer run
}
```

## Filesystem access is opt-in

`Runtime::new()` gives a script **no** way to touch the filesystem. An embedded
engine that can read anything is a very different security story from one that
cannot, and that claim is only worth making if it holds:

```rust
let mut rt = rlx_js::Runtime::new();
rt.eval("typeof rlx.readFile")?;   // "undefined"
rt.allow_filesystem();             // now it exists
```

The `rlx-js` CLI hands it over, because a script run from a shell already has
the user's authority. Training needs data, and a dataset loader is the one thing
a pure-graph API cannot supply — hence a real `readFile` rather than a bundled
fixture.

**Every** path-taking function is gated, not just `readFile`: `openGguf`,
`loadTokenizer`, `writeGguf`, `convertToGguf`, the weight loaders, the `.rlxp`
tools and `Trainer.save`/`load`. The first version of this claim was tested only
against `rlx.readFile` and was therefore false — a sealed runtime could read any
GGUF on disk and write one. Rendering a chat template from a *string* still needs
no permission; only a path is privileged.

## Data preparation

Three helpers do the per-element work natively, because that is the one place a
script touches tens of millions of values:

```js
const x = rlx.toFloat32(raw, { scale: 1 / (255 * std), bias: -mean / std });
const y = rlx.oneHot(labels, 10);
const batch = rlx.gatherRows(dataset, shuffledIndices, 784);
```

`toFloat32` dispatches on the input's **element type**, not on bytes — an
earlier version read everything as raw `u8`, so a `Float32Array` of three values
came back as twelve. `gatherRows` *borrows* its source; the first version copied
it and was 4× slower than the JS it replaced.

## A script cannot crash the host

An out-of-range node id used to go straight into `Graph::shape`, which indexes —
so `x.add(2)` on a two-node graph **panicked the process**. Every `node`-kind
argument is now checked against the graph, and the check is generated from the
same signature the argument reader is, so a new op is covered when it is
declared. An out-of-range id is a `RangeError`; the instruction budget bounds a
runaway loop. Both have tests.

## Backends

Feature gates mirror `rlx-runtime`: `cpu` (default), `metal`, `mlx`, `gpu`,
`cuda`, `rocm`, `vulkan`. Surface gates: `gguf`, `gguf-convert`, `weights`,
`training`, `text`, `graph-json`.

`new rlx.Session("cuda")` on a build without CUDA throws a `TypeError` naming
the feature to rebuild with. It never falls back to CPU — a silent fallback
turns a benchmark into a lie.

## Why embed an engine instead of shipping a Node addon

They answer different questions. A napi addon puts RLX inside someone else's
process and inherits npm, threads and an event loop. This puts a script inside
*ours*: one static binary, deterministic, no I/O a script can reach unless an
embedder hands it one, an instruction budget so a runaway loop cannot hang the
host — and it cross-compiles wherever RLX already goes, including iOS and wasm,
where a native addon cannot follow.

Config files, training recipes, eval harnesses and per-customer model wiring
are the shape that fits. To put RLX *inside* an existing Node service, a napi
addon is still the right tool; the two are complementary.

## Embedding

```rust
let mut rt = rlx_js::Runtime::new();
rt.set_instruction_budget(Some(50_000_000));   // bound untrusted scripts
let out = rt.eval("rlx.devices().join(',')")?;
```

`rlx_js::install(&mut ctx)` puts the namespace into a `Context` you already
own, for embedders adding globals of their own.

## Not here yet

Running a *model* (`Qwen3Runner` and family) is not reachable from JS, for the
same reason it is not from Python: those live in `../rlx-models`, which pins
published `rlx`. The binding for that belongs there, over the
`rlx_runtime::lm::LmRunner` trait and its `inventory` registry.
